\section{Final Project - \unit{I^2C} Memory}

\subsection{Introduction}

In this laboratory will cover the ability to comunicate to a memory peripheral via the I$^2$C protocol by implementing the required API functions that will be enabling this specific feature. The correctness of the implemented solution will wi tested and verified via the oscilloscope.

\subsubsection*{Object}

This lab exercise aims to develop the ability to write code that implements read and write operations via the I$^2$C protocol from the VirtLAB board, directed at a specific memory device on the secondary board.

In addition, this lab aims to verify the correctness of these operations by using a digital scope (DSO) to observe and analyze the generated signals, thereby assessing whether the communication was performed correctly.

For the accomplishment of this task the following instruments and hardware components where used:

\begin{enumerate}[label=\textbf{-}]
	\item Project template
	\item VirtLAB Mother board
	\item X-NUCLEO-EEPRMA1 Daughter board
	\item Rigol DS1054Z DSO
	\item Mounting equipment (i.e. breadboard, jumper cables, ect.)
\end{enumerate}

\subsubsection*{API Interface - \texttt{memInit}}

This first functions serves as a wrapper that calls the HAL initialing function for the interface that we enabled before in the previous configuration.\\

Here is the code of the implementation:\\

\begin{lstlisting}
int memInit(void) {

	I2CmemStatus = HAL_I2C_Init(&hi2c3); 
    return (I2CmemStatus == HAL_OK) ? 0 : -1;
    
}

\end{lstlisting}


\subsubsection*{API Interface - \texttt{memRead}}

In a second instance the API function to read the memory was implemented in the following way.\\

\begin{lstlisting}
int memRead(uint16_t memAddress, uint8_t *data) {

    I2CmemStatus = HAL_I2C_Mem_Read(&hi2c3, 
    								DEV_ADDRESS,
                                 	memAddress,
                                    I2C_MEMADD_SIZE_16BIT,
                                 	data,
                                    1,
                                    HAL_MAX_DELAY);
	osDelay(5);
    return (I2CmemStatus == HAL_OK) ? 0 : -1; 
}
\end{lstlisting}

\vspace{0.5cm}

With the API we created we are now able to call the HAL I$^2$C function given to us by the manufacturer (STMicroelectronics) and pass the the correct values to implement a single byte read operation.

In particular we are able to pass to the HAL function the interface, that we previously initialized, on which operate. 

In addition to that we have to specify the device address (U3 interface on the board) and then the memory address from which we want to read. 

Lastly the function needs the data (in this case is a pointer) where to put the data that was just read. In addition to all of these parameters the \texttt{I2C\_MEMADD\_SIZE\_16BIT} and \texttt{HAL\_MAX\_DELAY} parameters represent the size of the internal memory address and the maximum delay that the function waits before returning a timeout error. 

Obviously the parameter 1 was passed since we are implementing a single byte read operation.

The function then return 1 or 0 depending on the result that the HAL function has returned indicating a if the operation was successful or not.

\subsubsection*{API Interface - \texttt{mewWrite}}

After implementing the read API function we implemented the write one in the following way.\\


\begin{lstlisting}
int memWrite(uint16_t memAddress, uint8_t data) {

    I2CmemStatus = HAL_I2C_Mem_Write(&hi2c3, 
                                     DEV_ADDRESS,
                                     memAddress,
                                     I2C_MEMADD_SIZE_16BIT,
                                     &data,
                                     1,
                                     HAL_MAX_DELAY);
	osDelay(5);
    return (I2CmemStatus == HAL_OK) ? 0 : -1;
}		
\end{lstlisting}

\vspace{0.5cm}


With the API we created we are now able to call the HAL I$^2$C function given to us by the manufacturer (STMicroelectronics) and pass the the correct values to implement a single byte write operation.

In particular the values that are passed to the HAL function are simular to the one we have just introduced above. The only difference we have here consist in the data field which is now the data we want to write.
As before the functions returns 0 or 1 depending of the success of the operation.

\subsubsection*{Addressing}

Before moving on we want to clarify how the \texttt{DEV\_ADDRESS} parameter was obtained. This value represent the value of the address of the device we want to comunicate with over the I$^2$C protocol. \\

For this specific kind of memory device 2 pins (and not the typical 3) are used for getting an address. For our case pin E1 and E2 define the address that the memory can obtain: since are both connected to $V_{cc}$, logical value 1, the memory as the address 11 (since only 2 E pins are available there could be a maximum of 4, and not 8, devices over this I$^2$C bus).\\

Moving on: we know that the I$^2$C square protocol uses an 8 bit device address to select to which slave communicate to.
Provided on the device manual is the complete device addressing that can be followed to configure the address in the correct way.\\


Here is the table reporting what was present on the data sheets:

\begin{center}
\begin{tabular}{c c c c c c c c}
\textbf{b7} & \textbf{b6} & \textbf{b5} & \textbf{b4} & \textbf{b3} & \textbf{b2} & \textbf{b1} & \textbf{b0} \\
\hline

1 & 0 & 1 & 0 & 1 & 1 & 0 &  0 or 1 \\

\end{tabular}
\end{center}

The bits from \textbf{b7-b4} are the device identification number and are fixed for every type pd EEPROMs devices.
Then \textbf{b3} and \textbf{b2} are the chip select and corresponds to the E1 and E2 pins, so they are both set to 1. We note that the slave device on the I$^2$C square bus compares the address the master sends with the one it has set internally by pins like E1 and E2.

Moving on \textbf{b1} corresponds to the 17th addressing bit of the memory (this bit decides if the lower or higher part of the memory is being accessed). Since we are using 16-bit addressing we will set this to 0 and use only the first part of the memory matrix.

Lastly the \textbf{b0} bit is set either to zero or one for read and write operations.\\

As we can see we obtained the desired device address that will be used the I$^2$C protocol. We implemented that inside the firmware ad an hexadecimal value. Before moving on we note that since the read/write bit is part of the device address we will be logically addressing two different devices in read and write operations. Since addressing two different devices could be difficult and confusing the HAL functions helps us by requiring a 7-bit shifted to the left to which the correct HAL function will add the correct value of the read/write bit.\\

In the code we will find this implementation:\\

\begin{lstlisting}
#define DEV_ADDRESS_7_BIT 0x56 // 7-bit address no RW bit
#define DEV_ADDRESS (DEV_ADDRESS_7_BIT << 1) // Shift left for RW bit
\end{lstlisting}

\vspace{0.5cm}

As said before the last bit is not considered inside the device address so the address 1010110 in base two will be converted to hexadecimal (0x56) and then shifted to the left by one (\texttt{0x56 $<<$ 1}).\\

We can also find the value (8-bit) of the two logical address that the data will be read from and written to, these will be come useful later.

\begin{enumerate}[label=\textbf{-}]
	\item Read address is 10101101$_2$ =  0xAD
	\item Write address is 10101100$_2$ = 0xAC
\end{enumerate}

\subsection{Conclusions}
\label{concpf}


At this point we can come to conclusions part to explain the results obtained and if they differ from what we expected.\\

First of all we want to bring some observations that we have done during the course of the experience.\\

The first observation we want to bring up is the fact that by implementing the API prototypes given in the laboratory guide wi will never be able to address all of the memory since the 17th bit will never be used since it is part of the device address. In the case that the user would like to use 17-bit addressing with the given API it will be necessary to add some login to decide which device (at least on a logical way) will be addressed.\\

As a second observation since we are using the HAL functions given by the manufacturer they implement the safest possible mechanism to write and read data. This implementations causes that on every function call the MCU generate a START and STOP condition on the I$^2$C bus that forces the memory to execute an internal write on the memory matrix. This operation takes at most 5 ms and causes the memory to not respond to any SDA variation. This is the reason that forced use to implement a 5 ms delay after every function call to avoid accessing the memory when it will not be available. \\

We note that the HAL functions implements some kind of mechanism (given by the memory) to speed up writing operation when sending multiple byte that are on the same memory page. Due to the HAL function being so safe we were not able to test sone limit cases such as writing on different memory pages to see what happened at the protocol layer.\\

For the sake of completeness and out of curiosity we also tried to pool for the HAL\_OK status to be able to perform two sequential read via two different function call. This approach was later abandoned during the lab sessione to avoid any confusion created on the SDA line and since we did not care about the performance the 5 ms second delay was the way it was decides to proceed.\\

Coming now to the actual conclusion. We were able to implement a correct firmware that respected the API prototypes given inside the laboratory guide and some basic test cases to interface with the EEPROM memory via the I$^2$C protocol.\\

In a second phase we were also able to confirm via the DSO the predicted behavior of the SDA and CKL (100 kHz) lines.
As shown in the pictures given by the DSO we were able to write to the correct memory address the correct data and then read it by generating the correct START and STOP condition and by addressing the device and the memory accordingly.\\

In the end we noticed that the last two pictures, even if they represent reading operation, seem to be writing and then reading. This behavior is correct and its needed to preload the desired address inside the EEPROM memory (done via a dummy reading) and then generating a START condition followed this time by the actual reading operation (reading addressing) and the data being sent to the master of the bus (MCU).

Figured out this little problem we found out that all the reading and writing decoded by the DSO engine were correct and shown the device addresses we were expecting (\texttt{W:AC} and \texttt{R:AD}).\\

There are also some spike visible in the graph, these are due to the master releasing the line and checking where as the slave (EEPROM memory) takes it down to confirm the previously sent 8 bit of data. This operation might not be as smooth and sometimes the master releases the SDA line before the slave has pulled it to a low value thus creating those brief voltage spikes.
