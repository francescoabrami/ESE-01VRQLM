\subsection{Needed hardware}

We will now go over a very easy and simple explanation on the hardware setup.
Down below is a basic schematic of the setup that we will work on.

\subsubsection*{VirtLAB}

Let's begin with the hardware setup. First of all we need to connect the VirtLAB board to the power via the USB-C power supply (bottom left) and then power it by switching on the corresponding switch. When the board is turned off, only the green led labeled 5V is lit. When the board is turned on, adjacent green LEDs, labeled 3.3 V and 1.2V are lit, too.

After we have done that we can connect, via the micro USB to USB-A cable, the VirtLAB to the computer that will be used to program the MCU.
This connection is done via the STLINK (top left) that has the function of programming the MCU and be able to perform debug operation on the code.
This connection is where the \texttt{.elf} file, generated by our computer, will go through to be put inside the MCU.\\


\subsubsection*{STLINK}

The STLINK (in this specific case the STLINKV3) is the hardware device that is found on the top left of the board to which the MCU programming is done.
This is a device produced and sold by STMicroelectronics for the main purpose of being able to flash and debug firmware on an embedded system.
Obviously for learning reasons the device is soldered to the board but it is usually integrated in some kind od connector that is not permanent attached to system that we will be designing.\\

\subsection{Needed software}

Moving on to the software side this section contains a detailed list of software tools needed to use the VirtLAB. Hence, these programs must be installed on the PC physically connected to the VirtLAB.\\

For the sake of completeness we reported all sort of software but since this course is about embedded systems only the MCU software suite (STLinkbridge, STM32CubeIDE) will be used.\\

\subsubsection*{STLinkbridge}

Stlinkbridge is a \texttt{C++} command line application that uses the ST’s API in order to recognize the VirtLAB board and to connect the host to the embedded MCU programmer. 

Since the VirtLAB contains two MCUs, one of them needs to be chosen and specified as the one to be programmed. 

The stlinkbridge command allows the user to select the desired MCU. The executable is been  available inside the VirtLAB repository folder inside the online university portal and it can be found online very easily. Remember to check for which version you will be using, the VirtLAB board mounts the V3 version.\\

On the repository the files will be available inside the \texttt{code} folder of this laboratory following this path:

\[ \texttt{/Software/stlinkbridge/} \]\

Choose the subfolder corresponding to your operating system: \texttt{linux/}, \texttt{win64/}, or \texttt{macOSx/}. Copy the content of the downloaded folder in a suitable location on the host, accessible by the user. Desktop folder is strongly discouraged.\\

The following command is available to select the Master MCU:

\[ \texttt{stlinkbridge m} \hspace{2cm} \texttt{\#choose Master MCU} \]\


The following command is available to select the User MCU:

\[ \texttt{stlinkbridge u} \hspace{2cm} \texttt{\#choose User MCU} \]\



Both the command line and the VirtLAB GUI use these two commands. Hence, the stlinkbridge command must be accessible without having to specify the path to the stlinkbridge application.\\

To be able to run the command stlinkbridge you need to this procedure.
On MacOS, once having downloaded the file, you will move to the corresponding folder \texttt{/Software/stlinkbridge/macosx} you will find two \texttt{.dylib} file and a file named \texttt{stlinkbridge}.\\

We will now have to make this file executable, first of all move via the terminal to the directory where you have put these files and then run this command:

\[ \texttt{chmod +x stlinkbridge } \]\

By doing this the file will now be executable and can be run via the terminal with this command:

\[ \texttt{./stlinkbridge} \]\

By doing this MacOS might ask you to allow (multiple times) the execution of the program since is not coming from a known developer. To do this go to \texttt{Setting} and then \texttt{Privacy and Security}.\\

After we have done that we should be able to run the executable and this is what we should see with or without the VirtLAB board connected.\\


\begin{lstlisting}
Usage: ./stlinkbridge mode
    where mode can be:
    m: master MCU connected to STLink bridge
    u: user MCU connected to STLink bridge
    x: no MCU connected to STLink bridge
\end{lstlisting}

\vspace{0.5cm}

As we can see the command is asking us to insert a parameter such as \texttt{m}, \texttt{u} or \texttt{x} to proceed.
If this is not shown you might need to move the library files (the other two in the folder) to a specific location that the terminal will tell you. \\

The location is usually:

\[ \texttt{/usr/local/lib} \]\

It is strongly suggested to install the \texttt{stlinkbridge} file inside the following location on your system:

\[ \texttt{/usr/local/bin} \]\

By doing this you can run the command from any terminal window and from any directory. To check if this is correct open a new terminal window and run this command:

\[ \texttt{which stlinkbridge} \]\

This should return the location in which you just installed the stlinkbridge that is \texttt{/usr/local/bin}.\\

Now, only with the VirtLAB connected and turned on, you should be able to run the command, either with the \texttt{m} or \texttt{u} parameter, and get on screen a reading of the voltage supply of the board $V_{cc} \approx$ 3.3 V.
By changing the \texttt{m} or \texttt{u} parameters you should be able to see a VirtLAB LED turn on green for User and orange for Master configuration. Remember that we want to configure and program the User side.\\

At this point we can run, as after any time we connect and disconnect the board from our host machine, the following command:

\[ \texttt{stlinkbridge u} \]\

We remind that this can also be done via the VirtLAB GUI, more in this later on.



\subsubsection*{STM32CubeIDE}


This ST’s software IDE allows to program and compile some pieces of code, in order to create an ELF file, which will be then downloaded on the MCU.\\

The download link can be found here: \href{https://www.st.com/en/development-tools/stm32cubeide.html}{\texttt{https://www.st.com/en/development-tools/stm32cubeide.html}}

For this specific course the version that will be used is the 1.19.0 and on recent MacOS capable machines need to be interpreted via Rosetta II to be able tu run.\\

\subsubsection*{JDK}


The JDK contains tools for developing and running Java programs. It is necessary for running the VirtLAB GUI. If the GUI is not needed, then Java installation can be skipped. 

The software has been extensively tested with Java version 17. Older JDK releases are not acceptable at all. Newer versions will be tested in the near future, even if they could work. If JDK is already installed, you can check the current version with the following shell command:

\[ \texttt{java -version} \]\

Otherwise, go to \href{https://www.oracle.com/java/technologies/javase/jdk17-archive-downloads}{\texttt{https://www.oracle.com/java/technologies/javase/jdk17-archive-downloads}}, download the files for your operating system and install the development kit. 
Then, check the current version running the command \texttt{java -version} command.\\

\textbf{Note:} The JDK 8 is obsolete for this setup. Not all version were tested. However, it is well known that the JDK 17 fits: hence, JDK 17 is the recommended version.

\subsubsection*{VirtLAB GUI}


VirtLAB GUI is a Graphical User Interface, mandatory if FPGA configuration or master section instruments usage is needed. It is installed copying the content of folder /Software/VirtLabUI). This software is used to present a GUI controlling the VirtLAB, and performs the following functions:

\begin{enumerate}[label=\textbf{-}]
	\item  User interface of master section instruments (waveform generator, DSO, etc.)
	\item FPGA configuration support
	\item MCU programmer selection via stlinkbridge shell command
\end{enumerate}

It can be launched from the command line by using JDK, with the following command:

\[ \texttt{java -jar VirtLabUI-v1.3.jar} \]\

\textbf{Note:} This interface aims at simplifying the interaction with the VirtLAB, even if in theory, it is not strictly required.



\subsubsection*{STM32CubeProg}


This ST’s program is used for downloading the ELF file (created by Cube IDE) to the MCUs hosted by the VirtLAB board.

You only need to use STM32CubeProg to initialize the VirtLAB by programming the Master MCU (the first time you use it or if a firmware update is released) because only the ELF file is provided.\\

If the Master MCU already contains the firmware, you do not have to perform this
step. \\

When you develop your own code, you can directly and only use STM32CubeIDE for coding, creating the ELF file and downloading it to the MCU.\\


The download link can be found here: \\

\href{https://www.st.com/en/development-tools/stm32cubeprog.html#overview}{\texttt{https://www.st.com/en/development-tools/stm32cubeprog.html\#overview}}\\


\textbf{Note:} You must register on the STMicroelectronics web site to download the software.



\subsection{Firmare template}

At this point to finish our setup we can open the \texttt{STM32CubeIDE} program, select the template folder as the source at let the project load.

At this point we should be able to see all the projects file such as \texttt{main.c} inside the \texttt{/Src} folder and all of the header files inside the \texttt{/Inc} folder. \\

We remind that the template \texttt{virtlab-user} can be found inside the code section of the repository from which this file is generated from.

More specifically is here:

\[ \texttt{/Templates/virtlab-user} \]\

Once we are at this point, having the project open, we can click the build icon (hammer) and select either the release or debug version. Once the build is complete (no errors should occur), we can flash the MCU by clicking on the run icon (green play button).
At this point if the \texttt{stlinkbridge} command has been run after connecting the board the STLINK on the board should be flashing signaling the programming process.
Inside the STM32CubeIDE the ongoing operation should be visible and after less than a few second it should return a success condition.\\

At this point, having inspected the \texttt{application.c} code we can verify if it is correctly being run by checking if the LEDs on the VirtLAB board are flashing in an intermitting way with a 500 ms (half a second) period.
This is the demonstration that our code is being correctly programmed onto the MCU and that no errors occurred.\\

If this result is not obtained refer to laboratory our or after class time to ask for help.\\

\subsection{Introduction}

The purpose of this laboratory exercise was to analyze the performance of a microcontroller (MCU) that had been previously programmed with dedicated firmware. 

By performing various measurements - in release and debug mode - on the device’s input/output pins, characteristic system parameters were recorded and evaluated in order to verify its proper functioning and operational performance under various conditions.


\subsection*{Object}

The purpose of this report is to present and analyze the results obtained during the measurements performed throughout the laboratory session. After completing the measurement procedure, the collected data are examined and interpreted in order to assess their validity and consistency. Furthermore, the report aims to explain the observed results and discuss whether they are feasible and compatible with the expected behavior of the system under test.

\subsection{Conclusion}


From the data we gathered we can strongly say that there is, specially in high frequency task, a significant difference between the usage of LL functions instead of their HAL version. 
This is due to the fact that HAL functions provide a more safe, but also more complex and abstract, methods which is are present in LL function which usually operate directly over the device register with inline declarations.

Not only is the use of LL libraries faster than HAL libraries, but executing the code in release mode instead of debug mode can also lead to significant performance improvements. 
This is clearly observable in almost all the performed tests, where the frequency of the generated signal and the measured timing differ substantially between configurations. In particular, the signal frequency is often approximately doubled or halved depending on the case, highlighting the strong impact of compiler optimization and build configuration on overall system performance.
